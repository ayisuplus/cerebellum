# Offline Skill Evolution Dry-Run Design

## Requirement

Build the first version of Evolver's skill evolution upgrade as an offline dry-run tool for the project owner and local agents.

The tool must prove that a generated or existing skill is ready for future GEPA optimization without calling external model APIs, importing DSPy, writing databases, modifying the source skill, or touching Hermes Agent paths.

### Users

- Primary user: the project owner running Evolver locally.
- Secondary user: coding agents that need a deterministic preflight before implementing real optimization.

### Functional Requirements

- Load one skill markdown file from an explicit path.
- Parse skill frontmatter and body into a structured artifact.
- Build an evaluation dataset from either manual JSONL or existing Evolver memory recall.
- Validate skill structure, dataset shape, size limits, and split completeness.
- Write a run directory containing baseline content, dataset, report, and human-readable summary.
- Return deterministic CLI exit codes for pass and fail states.

### Non-Functional Requirements

- No external optimizer dependency in Phase 1: no DSPy, GEPA, OpenAI, Anthropic, MiniMax, or network requirement.
- No runtime path changes: existing `SkillEngine.generate()` behavior remains unchanged.
- No database migrations in Phase 1.
- No automatic overwrite of source skill files.
- Machine-readable output must be stable enough for later agents to consume.
- The design must keep a clear seam where Phase 2 can add real GEPA optimization.

### Fit Criteria

- `evolver evolve-skill --skill-path <file> --dry-run` succeeds with a valid skill and valid dataset source.
- The same command fails with exit code `2` for invalid skill format or invalid dataset input.
- The command creates exactly one run directory per invocation and never overwrites the source skill.
- Tests cover artifact parsing, dataset loading/building, constraints, and CLI behavior.

## Specification

### Scope Decision

Phase 1 is an offline dry-run MVP. It verifies the optimization pipeline skeleton, not skill quality improvement.

Accepted:

- Add a small offline skill evolution module.
- Add one CLI command for dry-run preflight.
- Add deterministic dataset and constraint validation.
- Add local file output under an explicit output directory.

Deferred:

- Calling GEPA or MIPROv2.
- Adding DSPy or LLM dependencies.
- Writing evolution history tables.
- Integrating into `SkillEngine.generate()`.
- Writing to `~/.hermes/skills/`.
- Batch optimization.
- Automatic weak-skill discovery.

Rationale: the reference project operates as an external optimization pipeline. Evolver should first prove that local artifacts, datasets, constraints, and reports are reliable before introducing API-dependent optimization. This keeps current learn/recall/skillgen flows stable and avoids turning normal skill generation into a slow, costly path.

### Architecture

```text
skill file / generated skill
        |
        v
SkillArtifact loader
        |
        v
EvalDatasetBuilder
        |
        v
ConstraintValidator
        |
        v
DryRunReport writer
        |
        v
output/evolution-runs/<skill-name>-<timestamp>/
```

The dry-run path is independent from the existing `SkillEngine` runtime path.

Rationale: a separate path limits blast radius. The tool can be used on any skill file, including skills generated by `skillgen`, without changing how skills are produced today.

### Components

#### EvolutionConfig

Holds run configuration:

- `skill_path`
- `db_url`
- `dataset_path`
- `dataset_source`
- `output_dir`
- `max_skill_size`
- `dry_run`

Rationale: explicit config makes the later GEPA implementation a plug-in behind the same preflight interface.

#### SkillArtifact Loader

Reads a markdown skill file and extracts:

- `path`
- `raw`
- `frontmatter`
- `body`
- `name`
- `description`
- `size`

The loader rejects missing files, missing frontmatter, missing `name`, missing `description`, or empty body.

Rationale: Phase 2 optimizers need a stable artifact boundary. Parsing should fail early before dataset or optimizer work starts.

#### EvalDatasetBuilder

Builds `EvalExample` entries with:

- `task_input`
- `expected_behavior`
- `category`
- `source`

Supported sources in Phase 1:

- `manual`: load JSONL from `dataset_path`.
- `memory`: use Evolver recall for the skill name or topic, then derive deterministic rubric examples from returned memories.

Manual JSONL requires `task_input` and `expected_behavior` on every line. Memory source requires at least 3 examples after recall.

Rationale: manual datasets provide precise tests when available. Memory datasets are Evolver's unique wedge: evaluation material comes from accumulated experience rather than only static skill text.

#### ConstraintValidator

Checks:

- skill is non-empty.
- frontmatter has `name` and `description`.
- body has at least one workflow-like section such as `## Steps`, `## Workflow`, or `## Usage`.
- raw skill size is within `max_skill_size`.
- dataset has at least one train, val, and holdout example.
- every example has required fields.

Rationale: constraints are hard gates. A dry-run that passes should mean a later optimizer has enough structure to proceed safely.

#### DryRunReport Writer

Creates:

```text
output/evolution-runs/<skill-name>-<timestamp>/
├── baseline.md
├── dataset.jsonl
├── report.json
└── README.md
```

`report.json` contains:

- `status`: `pass` or `fail`
- `skill_name`
- `skill_path`
- `dataset_source`
- `counts`: train, val, holdout, total
- `constraints`
- `errors`
- `warnings`
- `next_phase_ready`

Rationale: reports must be readable by humans and stable for agents. `next_phase_ready` gives Phase 2 a clear handoff signal.

### CLI

Add:

```bash
evolver evolve-skill --skill-path <path> --dry-run --db-url <url> --output-dir output/evolution-runs
```

Optional:

```bash
evolver evolve-skill --skill-path <path> --dry-run --dataset-path <path.jsonl> --dataset-source manual
```

Exit codes:

- `0`: dry-run passed.
- `2`: input, skill format, dataset, or constraint failure.
- `1`: output write failure or unexpected internal failure.

Rationale: distinct exit codes make the command safe for agents and scripts.

### Data Flow

```text
CLI args
  |
  v
load skill artifact
  |
  +--> write baseline.md
  |
  v
build eval dataset
  |
  +--> manual JSONL or memory recall-derived examples
  |
  v
validate constraints
  |
  +--> skill constraints
  +--> dataset constraints
  +--> config constraints
  |
  v
write report and README
```

Memory dataset derivation is deterministic in Phase 1:

- Recall related memories by skill name or topic.
- Convert each memory into one `EvalExample`.
- Set `task_input` from the memory content or a concise deterministic prefix.
- Set `expected_behavior` to a rubric that requires covering the lesson and avoiding the failure mode described by the memory.
- Split examples in stable order: first 60% train, next 20% val, final 20% holdout.

Rationale: deterministic generation avoids model dependency while still using Evolver memory as the differentiator.

### Error Handling

Named errors:

- `SkillLoadError`: file missing, not a file, or unreadable.
- `SkillFormatError`: missing frontmatter, `name`, `description`, or body.
- `DatasetError`: JSONL parse failure, missing fields, or too few memory examples.
- `ConstraintError`: size, section, or split validation failure.
- `OutputError`: run directory or report write failure.

The CLI prints a concise error and writes a fail report only when the run directory can be safely created. It never writes a passing report after any error.

Rationale: every failure path must be visible and attributable. A failed dry-run should tell the next agent exactly what to fix.

### Testing

Use test-driven development.

Planned tests:

- `tests/test_skill_evolution_artifact.py`
- `tests/test_skill_evolution_dataset.py`
- `tests/test_skill_evolution_constraints.py`
- `tests/test_cli.py`

Coverage requirements:

- parse valid skill frontmatter.
- reject missing `name` or `description`.
- reject empty body.
- load valid manual JSONL.
- reject JSONL with missing required fields.
- reject memory dataset with fewer than 3 examples.
- pass valid skill and valid dataset constraints.
- fail oversized skill, missing workflow section, or empty split.
- CLI success creates a run directory and report.
- CLI failure returns non-zero and does not create a misleading pass report.

Verification command:

```powershell
$env:PYTEST_DISABLE_PLUGIN_AUTOLOAD='1'; python -m pytest tests/test_skill_evolution_*.py tests/test_cli.py -v
```

### Phase 2 Seam

Phase 2 can add a real optimizer behind the same preflight outputs:

```text
Dry-run pass
    |
    v
OptimizerAdapter
    |
    +--> GEPAAdapter
    +--> MIPROAdapter
    +--> NoopAdapter
```

Only Phase 2 should add optional dependencies such as DSPy or model clients, and those should live under an optional dependency extra rather than the core install path.

Rationale: keeping the optimizer behind an adapter prevents external dependencies from leaking into normal Evolver usage.

### 10x Direction

The later 10x version should automatically discover weak skills by reading skill evaluation history, memory failure patterns, and repeated recall themes. Phase 1 should not implement discovery, but reports should include enough structured fields for a later selector to rank candidates.

### Out Of Scope

- Direct Hermes Agent integration.
- Automatic PR generation.
- Cost tracking for real model calls.
- LLM-as-judge scoring.
- Semantic embedding similarity checks.
- Database-backed evolution history.

These are valuable only after the dry-run path proves repeatable.
